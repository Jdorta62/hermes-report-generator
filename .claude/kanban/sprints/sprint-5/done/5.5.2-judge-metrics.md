**Citation mapping (item 4) — what I found, against `hermes_generator` 's installed source:**
- `[n]` IS the n-th context piece, 1-based. Three places agree: `build_messages` numbers the prompt blocks `<source n="{number}">` with `enumerate(request.sources, 1)`; `parse_answer` validates a marker with `1 <= n <= source_count`; `Answerer` builds `Citation(number=n, chunk_ids=pieces[n - 1].chunk_ids)` and `source_pieces` numbers `SourcePiece.number` from 1. So the 1:1 mapping of design §2 holds and `citation_targets` keeps it.
- `GenerationResult.citations` is `tuple[hermes_core.generation.Citation(number, chunk_ids)]`: unique numbers in order of first appearance, answer-wide. It carries NO claim-to-piece link and no more information than the `[n]` markers of the answer text (`number` equals the marker), so it is not a different mapping. `MetricInput.citations` therefore stays `None` for runs (the adapter of 5.5.3 should pass `None`; `explicit_citations` of design §7 has nothing to return). The override in `citation_targets` stays for a caller that has a real marker-to-piece map.
- Two caveats for the notebook/adapter tasks: (1) with `citation_style="none"` the generator REMOVES the markers from `answer` (they only survive in `citations`), so the claims carry no markers and `citation_precision`/`citation_recall` come out `None`; (2) invalid markers (outside the sources) are also removed from `answer` and listed in `invalid_citations`, so `piece=0` only happens for judge-invented markers.

**Design decisions:**
- `citation_targets` returns one `Citation` per distinct marker of each claim, in claim order (flat); the metric groups per claim through the private `_per_claim`. With `item.citations` given, a claim marker is looked up there by `marker` (absent gives piece 0).
- `JudgeSession.ask` now catches `Exception` (not a closed tuple): any client/parse failure becomes a logged, memoised `MetricError`. A non-`str` reply raises `MetricError` and is logged as `repr(raw)` so it is not lost. `parse_*` also never raise anything but `MetricError`.
- `judge.py` imports `prompts` lazily inside the four new methods: `prompts` needs `Claim`/`ClaimVerdict` from `judge` at runtime (design puts them there), so a top-level import would be circular.
- `verify` returns `()` for no claims and all-unsupported verdicts for no sources, without a judge call. The memo key is `verify:<key>` (also the call `purpose`), so a free-form key never collides with `answer_claims`.
- Each judged metric puts `judge.calls_since(mark)` in `MetricResult.calls` on success too (the calls it triggered; memo hits add none); on failure `evaluate_metrics` does it as before.
- Edge cases not fixed by the design: `faithfulness` is `not_applicable` when `item.refused`; `context_recall` with no expected claims gives `None`; `answer_correctness` with no expected claims gives all three `None`, with no answer claims gives precision `None`, recall `0.0`, F1 `0.0`; `citation_precision`/`recall` are `None` with no citations / no supported claims. Duplicate markers inside one claim are collapsed; an unsupported verdict may still list sources (ignored by `Citations`, which needs `supported`).
- `AnswerCorrectness.scores` is precision, recall, F1 (design table order), so the primary score is `correctness_precision`.
- Optional-family prompts (`entities`, `flag`) are not here: the task lists only claims, verify, relevance and questions.
