## Tarea

Create the package `src/hermes_report/metrics/` with its core and the four
deterministic metric families. Design §4 (`base`, `judge`, `selection`,
`runner`, `deterministic`), §5 and §7.

1. **`metrics/base.py`**: `METRIC_STATUSES`, `INPUT_FIELDS`, `MetricError`,
   `RankedChunk`, `Citation`, `MetricInput` (with `has()`), `JudgeCall`,
   `MetricServices`, `MetricResult` (with `not_applicable`, `skipped`,
   `failed`, `to_record`) and the `Metric` Protocol (`reg: metric`).
2. **`metrics/judge.py`**: `Claim`, `ClaimVerdict` and `JudgeSession`
   with `ask` (memo by key; a failure is memoised and re-raised;
   every call logged as a `JudgeCall`) and `calls_since`. The higher
   operations (`answer_claims`, `expected_claims`, `verify`,
   `chunk_relevance`) come in 5.5.2; leave them out here.
3. **`metrics/deterministic.py`**: `doc_retrieval`, `evidence_retrieval`,
   `refusal` and `cost`, with the definitions of design §4. Evidence
   matching reuses `Question.reachable` and `normalise` from
   `hermes_report.questions`. Tokens use a `hermes_enrich` `TokenCounter`
   (`MetricServices.counter`).
4. **`metrics/selection.py`**: `METRICS` (registry in design-table
   order, only the families implemented so far), `MetricSelectionError` and
   `MetricSelection.resolve`.
5. **`metrics/runner.py`**: `evaluate_metrics` (never raises:
   `not_applicable`, `skipped`, `error` as in §7) and `aggregate` /
   `ScoreSummary`.
6. **`metrics/__init__.py`** re-exports the public names of design §4
   that exist after this task.
7. `.api` files.

**Acceptance criteria**
- Every deterministic score matches hand-computed values on small fixtures:
  hits at rank 1, at rank k and none; evidence split across two chunks;
  evidence retrieved but not in the context (`budget_loss` > 0); refusal
  and non-refusal questions; chunks without `source`
  (`not_applicable`).
- A metric that raises yields `status="error"` and the next metric still
  runs; a failed `JudgeSession.ask` is not called again for the same key.
- `resolve` honours default-on, `include`, `exclude`, `enabled=False`,
  and rejects unknown names.
- `aggregate` counts `not_applicable`, `skipped` and `errors` apart and
  averages only real values.
- `uv run just check` is green.

**Design decisions:**
- `JudgeCallRecord` / `MetricResultRecord` live in `record.py` as the design says, but are added now because `to_record` returns them. Task 5.5.4 still adds `ScoreSummaryRecord`, `MetricsRunRecord`, the `metrics` fields, schema 2 and `READABLE_SCHEMAS`.
- `describe(exc)` is public in `base.py` (the design pseudocode uses it in `judge` and `runner`; `providers._describe` is private).
- `MetricServices.judge` is typed with `JudgeSession` through a `TYPE_CHECKING` import (base <-> judge would otherwise be circular).
- `MetricResult.to_record` flattens `details` to plain data (dataclasses, tuples, sets -> dicts/lists) so later judged metrics can put `Claim`s there and still get a JSON-safe record.
- `MetricInput.has` raises `ValueError` for a name outside `INPUT_FIELDS`; `evaluate_metrics` catches it (a bad `requires` becomes an `error` result, never an exception).
- `not_applicable` / `skipped` / `failed` results have empty `scores`; `aggregate` counts them from `status`.
- `doc_retrieval` is `not_applicable` (missing `["source"]`) when no retrieved chunk has a source. Document matching is exact on `source`, like `RuleRecord.expected_docs_retrieved`.
- Evidence ranks join chunks (and the context) with `"\n"`, the separator the rules use; with an empty context `evidence_recall_context` is 0.0 and `budget_loss` equals the recall (design formula, literal).
- `cost`: a phase missing from `seconds`, and tokens of an empty context / prompt / replies, are `None` (no data), not 0, so they stay out of the mean. Token values are floats.
- `refusal`: `false_refusal` is 1.0 only when refused, not a refusal question and the evidence is reachable in the context (so a question without evidence gives `None`); 0.0 when it did not refuse. `invented_answer` mirrors it for refusal questions.
- `ask` re-raises the very same memoised `MetricError` instance; a provider/JSON/parse failure is logged once and never repeated for the same key.
- `JudgeSession._item` is stored but unused until 5.5.2.

**Edge cases detected without coverage:**
- A `parse` callback that raises something other than `MetricError`/`ValueError` (for example `KeyError` on a missing JSON field), or a client that returns a non-`str` (`json.loads(None)` -> `TypeError`), escapes `JudgeSession.ask` without being logged or memoised. I confirmed it: two asks make two judge calls, `calls` stays empty and the raw reply is lost. This matches the design pseudocode (it only catches those three types), and `evaluate_metrics` still turns it into an `error` result, so it is not a failure here. It breaks "a failed ask is not called again" and "every call is logged" as soon as a 5.5.2 `parse_*` raises a bare `KeyError`/`TypeError`. Recommendation for 5.5.2: parsers must wrap everything in `MetricError`, or widen the `except` in `ask` to `Exception`. Not pinned by a test so as not to freeze the gap.
- `to_record` with `NaN`/`inf` in scores or details: `NaN != NaN` breaks the "equals its JSON round trip" promise. Current metrics never produce them (token and ratio values only); a future embedder-based metric might.
- `_plain` turns a `set` into a list in iteration order, so a set of strings gives a run-dependent order in the record (the test sorts it). Only matters if a later metric stores a set in `details`.
- Thread safety of `JudgeSession` (shared memo/log): not covered; the runner is sequential today.
- `DocRetrieval` matches `source` exactly (no path normalisation, no case folding): tested as such; if the corpus loader ever yields `docs/a.md` while questions say `a.md` the metric silently scores 0. Same behaviour as the rules, so left as is.
- Direct `compute()` calls with empty `documents`/`evidence` raise `ZeroDivisionError`; only the `requires` guard in `evaluate_metrics` prevents it. Acceptable per the contract (`requires` is checked by the runner), not tested.

**Verdict:** PASS — all acceptance criteria are covered by hand-computed fixtures and pass, coverage is 100%, no defect found against the design; one robustness gap in `ask` is flagged above for 5.5.2.
