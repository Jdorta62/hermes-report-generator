## Tarea

Compute the metrics in `hermes-report run` and store them in `run.json`
schema 2. Design §4 ("Changes to existing modules") and §7 (`metric_input`).

1. **`metrics/adapter.py`**: `metric_input(question, record)`. Refusal
   detection must be the same test the rules use for `generation_refused`.
2. **Config**: `MetricsConfig` (`[metrics]` with `enabled`, `include`,
   `exclude`) in `RunConfig`, `to_dict`/`to_toml` round trip; unknown
   metric names are a `ConfigError` with key `metrics.include` /
   `metrics.exclude`. `Overrides.no_metrics` and `Overrides.metrics`
   (added to include).
3. **CLI**: `run --no-metrics` and `run --metric NAME` (repeatable).
4. **Record**: `SCHEMA_VERSION = 2`, `READABLE_SCHEMAS = (1, 2)`, the new
   TypedDicts, `QuestionRecord.metrics` and `RunRecord.metrics`
   (selection, scores, summary). `read_record` reads schema 1 and fills
   `metrics=None` on the run and on each question.
5. **Runner**: after the judge of each question, build the input, run
   `evaluate_metrics` with a fresh `JudgeSession` (or `None` with the
   judge disabled), the run's embedder and the enrich token counter; at the
   end, `aggregate`. A question whose pipeline raised still gets metrics
   (most `not_applicable`).
6. Update §3.1, §6 and §9 of `designs/report-generator/design.md` only if
   the architect asks; otherwise leave it. `.api` files.

**Acceptance criteria**
- `examples/demo/run-offline.toml` writes a schema-2 `run.json` with
  metrics on every question and a summary.
- `--no-metrics` writes `metrics: null`; `--no-judge` keeps only the
  deterministic families (judge ones `skipped`).
- A schema-1 `run.json` (fixture) still reads, and `render` gives the same
  HTML as before for it.
- `uv run just check` is green.

## Contexto

**Carry-over from 5.5.2** (Manuel checked `hermes_generator`):
- `[n]` is the n-th context piece, 1-based. `GenerationResult.citations` is an answer-wide, deduplicated list of `Citation(number, chunk_ids)` with no claim-to-piece link, so `metric_input` passes `citations=None` and lets `citation_targets` derive them from the markers.
- With `citation_style="none"` the generator strips the markers, so `citation_precision` / `citation_recall` come out `None`. Carlos pins that through `metric_input` here (it could not be tested in 5.5.2 without the adapter).

**Design decisions:**
- `RunConfig.metrics` has a default (`MetricsConfig()`) and sits with the other defaulted fields, so code that builds a `RunConfig` by hand keeps working.
- `_as_metric_names` imports `METRICS` inside the function: `metrics/__init__` -> `judge` -> `providers` -> `config` would be a cycle at import time.
- `metrics` in the record is `None` only when `[metrics] enabled = false` (or `--no-metrics`). Enabled with every family excluded gives an empty selection, `[]` on each question and an empty summary.
- Metrics run also for a question whose pipeline raised (`metric_input` tolerates missing phases); `RunOutcome.failed` and the rule/judge records are untouched.
- A new schema error message lists the readable versions ("se esperaba 1 o 2").
- Offline demo (`run-offline.toml`): `EchoJudgeClient` still answers only the verdict JSON, so every judged family (faithfulness, answer_relevance, context_precision/recall, answer_correctness, citations) is recorded as `error` on all 7 questions (strict parsing). The deterministic ones are `ok`. I did not change `EchoJudgeClient` (tests of 5.5.2 pin it).
