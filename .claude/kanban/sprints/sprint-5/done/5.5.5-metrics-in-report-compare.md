## Tarea

Show the metrics in `report.html` and `compare.html`. Design §4
("Changes to existing modules").

1. **`render/html.py`**: `METRIC_LABELS` (Spanish label per score) and
   `LOWER_IS_BETTER`.
2. **`render/score.py`**: `metric_tiles(record)`, one tile per score with
   a mean (two decimals, plus `n` and errors when there are any); `()`
   for schema 1.
3. **Resumen**: the metric tiles below the current ones, and one column per
   family (its primary score, the first in `Metric.scores`) in the
   question table.
4. **Question tab**: a "Métricas" section: per family its status, scores,
   details (claims, verdicts, generated questions, citations...) and the
   judge calls in raw form.
5. **compare**: the metric tiles per run and one matrix row group per score;
   runs without metrics (schema 1) show `NO_DATA`.
6. `.api` files.

**Acceptance criteria**
- The HTML is still byte-identical for the same `run.json` and still
  escapes every recorded text.
- A schema-1 record renders exactly as before this epic.
- Lower-is-better scores are marked as such.
- `compare` of a schema-1 run and a schema-2 run works.
- `uv run just check` is green.

## Contexto

**Carry-over from 5.5.4** (José approved it, 2026-10-23):
- `EchoJudgeClient` (`providers.py`) always replies the rule-judge verdict JSON, so in offline runs every judge-based metric family ends in `error` on every question, and the demo report would show no judge metrics. Make it answer each metric operation with a valid, deterministic reply:
  - recognise the operation from the JSON shape that the system message of `metrics/prompts.py` asks for (claims, verify, relevance, questions, entities, toxic, biased), and keep the current `partial` verdict reply for the rule-judge prompt of `evaluate.py`;
  - derive the reply from the numbered texts of the user message, so that counts and indexes always match what `parse_*` validates (for example, one claim per sentence of the text, each claim supported by source 1, every chunk relevant, the question itself repeated as generated questions, no toxic or biased flags);
  - stay offline, deterministic and free of randomness.
- `runner.run` guards only `evaluate_metrics`: if `metric_input`, `MetricSelection.resolve` or `aggregate` raised, the whole run would crash without writing `run.json`. Wrap the per-question metric block so a failure leaves that question with `metrics: None` and a progress warning, and a failing `aggregate` leaves an empty summary. Metrics never change the run (Carlos, 5.5.4 review).

- Acceptance: `examples/demo/run-offline.toml` gives `status="ok"` for every default-on judge family on the questions where its inputs exist, and the report shows their means. The existing tests of the rule judge with `EchoJudgeClient` still pass unchanged.

**Design decisions:**
- No CSS/JS change: the schema-1 golden `tests/fixtures/schema1/report.html` inlines both, so any asset change would break it. The new markup reuses existing classes (`tile`, `big small`, `status`, `verdict`, `msg`, `error`, `text raw`).
- Schema-1 records render byte-identically: every new piece is empty when `metrics` is `None`/missing (checked against the golden; `.get("metrics")` is used so hand-built records without the key also work).
- Metric tile value is `"0.83 (n=5)"`, with `", 2 errores"` appended when a metric failed; lower-is-better labels end with ` ↓`.
- Primary score of a family comes from the `METRICS` registry (`scores[0]`); a family the registry does not know falls back to the first score any question recorded.
- Matrix: score groups sit in the same table after the question rows; their rows carry no `data-q`, so the "solo filas con diferencias" filter leaves them alone.
- `EchoJudgeClient` replies: claims = one per sentence (a `[n]` marker after the full stop goes back to the previous claim; expected-answer prompts get `citations: []`), verify = every claim supported by source 1, relevance = every chunk relevant, questions = the first sentence of the answer as a question, repeated n times (the question text is not in that prompt), entities = capitalised words and numbers of the text, toxic/biased = false. Counts are read from the numbered blocks (`[1] ...`), so `parse_*` always accepts them.
- Offline demo (`examples/demo/run-offline.toml`, checked with all six opt-in families too): every family is `ok` on every question where its inputs exist; the report shows their means.

**Edge cases detected without coverage / known limits:**
- `EchoJudgeClient` cannot tell a chunk containing a line like `[2] ...` (for example a markdown reference list) from a second chunk, so `relevance` miscounts and that family ends in `error` for the question (graceful, never a crash). Inherent to the numbered-text encoding, so not a blocker. Pinned by a strict `xfail` (the desired behaviour) plus a test that the miscount is a `MetricError`, not a crash. Same for a question/expected text that contains `"\n\nFragmentos:\n"`. Worth a line in the `EchoJudgeClient` docstring ("always" is too strong).
- Claim texts from the echo judge may carry a space before the full stop when a `[n]` marker sat between ("Nace en Albarracín ."); cosmetic, not pinned.
- A question whose metric block was guarded (`metrics: None`) counts as `not_applicable` in `aggregate`; the summary still adds up to the number of questions. Pinned.
- After a failed `resolve`, questions get `metrics: []` (not `None`); the report treats both the same. Pinned.
- A metric-only difference between runs does not highlight a matrix row (`diff` considers verdicts only). Pinned as current behaviour; confirm it is the intent.
- The pre-existing comment in `test_metrics_judged.py::TestWithEchoJudge` ("The echo reply fits no judge shape") is now stale; the test still passes. Not touched (other task's file).
- Coverage via `just cov` with several dotted submodule names failed with a numpy "cannot load module more than once" error; I measured with `--cov=hermes_report` instead.
